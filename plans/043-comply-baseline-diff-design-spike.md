## Why this matters (product framing, not a bug)

`hermex comply` is all-or-nothing: any `error`-severity violation fails the
build, with no way to say "don't fail on debt that already existed, only on
*new* debt introduced by this change." Teams adopting hermex on an existing,
non-compliant codebase can't turn on `comply` as a CI gate without either
fixing every existing violation first (often infeasible) or leaving it as
`warn`-only forever (no enforcement). A baseline/diff mode — "fail only on
violations not present in a reference baseline" — is the standard pattern
for incremental adoption of any new lint/compliance gate. hermex already
has a `versus` feature (`src/utils/versus.ts`) tracking package-migration
percentages between two named groups, which shows the project's general
comfort with "comparison" framing, but **`versus` is not directly reusable
code for this** — it diffs usage percentages between two *package name
groups* in a single run's data, not violations between two *points in
git history*. This spike should not assume `versus`'s implementation
transfers; treat it as evidence of product fit, not a code starting point.

## Current state

**`src/utils/compliance.ts`** (full file, 43 lines) — `computeCompliance`
takes one `AggregatedReport` and returns pass/fail plus the three violation
categories (`errorRuleViolations`, `errorBannedPackageViolations`,
`releaseAgeViolations`). This is the function a diff mode needs to call
**twice** (once for the current tree, once for the baseline) and then
compare.

**`src/rules/shared.ts:5-25`** (`RuleViolation`) — **no stable identity
field**. `matchedFiles: string[]` plus `type`/`patterns` is the closest
thing to an identity, but two different violations of the same rule type
against overlapping-but-not-identical file sets have no clean way to say
"is this the same violation, grown/shrunk, or a genuinely new one?" This is
the central design problem this spike must solve (see Step 1 Q2).

**`src/commands/comply.ts:67-109`** (`executeComply`) — where a
`--baseline`-equivalent flag would need to branch: currently runs
`runPipeline` once, computes compliance once, sets exit code once.

**`src/utils/versus.ts`** (full file, 49 lines) — confirmed NOT directly
reusable (see "Why this matters"); included here only so the spike doesn't
waste time investigating it as a code source.

**No existing git-ref-checkout machinery** exists anywhere in this
codebase (confirmed via repo-wide grep for `simple-git`, `isomorphic-git`,
or raw `git` subprocess calls in `src/` — none found). Obtaining a
baseline's violations means either (a) shelling out to git to check out a
different ref into a temp directory and re-running the pipeline there, or
(b) reading a **pre-computed baseline snapshot file** committed/cached
somewhere (e.g. generated by a separate CI job on `main`, uploaded as an
artifact, downloaded by the PR job). This is the second central design
question (Step 1 Q1).

## Steps

### Step 1: Answer these design questions in `docs/design/comply-baseline-diff.md`

1. **How is the baseline obtained?** Two real options:
   - **(a) Live git checkout**: shell out to `git worktree add` (or a
     temp `git checkout` in a scratch clone) for the baseline ref, run the
     full hermex pipeline there, compute its `ComplianceResult`. Pro: always
     fresh, no separate CI plumbing. Con: doubles `comply`'s runtime (full
     scan + optional registry enrichment, twice), requires a working git
     repo with the baseline ref fetched (shallow CI checkouts often don't
     have it — `actions/checkout` needs `fetch-depth: 0` or an explicit
     `git fetch origin main`).
   - **(b) Pre-computed snapshot file**: a separate CI job (on `main`,
     post-merge) runs `comply --format json` (or a new
     `--write-baseline <path>` flag) and uploads/commits the result; the PR
     job downloads/reads it and diffs against the current run. Pro: PR job
     only scans once. Con: requires new CI plumbing (an artifact or a
     committed file), and the snapshot can be stale if `main` moved since
     it was generated.

   Recommend one, with reasoning grounded in this repo's existing CI shape
   (`.github/workflows/pull-request.yaml` already runs a `coverage` job
   that checks out `main` a second time for a comparison baseline —
   `matrix: include: - branch: main` — this is a **directly applicable
   existing pattern** worth reusing structurally for option (a), since the
   repo already pays the "check out main a second time in CI" cost for
   coverage comparison).

2. **Violation identity — what makes two violations "the same" across
   runs?** Since `RuleViolation` has no stable ID, propose a fingerprint
   scheme, e.g. `` `${type}:${severity}:${patterns.join(',')}:${file}` ``
   computed **per matched file** (splitting `matchedFiles: string[]` into
   one fingerprint per file, since a rule violation "growing" to cover one
   more file should show as one new fingerprint, not invalidate the whole
   violation). Address: what happens when a rule's `message` or `patterns`
   config changes between baseline and current (does that count as
   "different rule" or "same rule, reconfigured")? Recommend patterns+type,
   not message, as the identity (messages are free-text and shouldn't
   affect diffing).
3. **BannedPackageViolations and releaseAgeViolations** — do these use the
   same fingerprint scheme (package name + violation kind), or something
   package-specific? Release-age in particular is time-dependent (a
   package can newly breach a threshold purely because more days passed,
   with zero code change) — should a release-age violation that "aged into"
   breach count as "new" (technically true) or be excluded from baseline
   diffing entirely (arguably more useful — code changes vs. calendar time
   are different categories of "new")? Recommend excluding release-age from
   the diff (always evaluated against current thresholds, not diffed) and
   only diffing rule violations and banned packages — state the reasoning
   explicitly in the doc since this is a real product judgment call, not
   an obvious technical default.
4. **CLI/config surface**: `comply --baseline-ref main` (triggers live
   checkout, option a) vs `comply --baseline-file baseline.json` (reads a
   snapshot, option b) vs a new `output.baseline` config block? Recommend
   based on the Step 1 Q1 decision.
5. **Exit code semantics**: does "new violations only" mode still use exit
   codes `0`/`1`/`2` the same way, just computed against the diff instead of
   the raw violation list? Confirm yes/no and why.

## STOP conditions

- The fingerprint scheme from Step 1 Q2 produces false "new violation"
  noise on a case you didn't anticipate while writing the tests in Step 3
  (e.g. file renames, or rule `patterns` that are dynamically generated) —
  document the edge case in the design doc rather than shipping a
  fingerprint scheme known to be noisy.
