### Reconciliation 2026-08-15 (commit `688c481`) — full audit, plans 030–038

Run under [#111](https://github.com/Gallevy/hermex/issues/111) on the v3 map.
13 findings, all vetted against the code. Full evidence:
[`docs/research/improve-audit-2026-08-15.md`](../docs/research/improve-audit-2026-08-15.md).

The findings were first triaged onto map tickets rather than into plan files,
because 10 of the 13 landed on **grilling** tickets — open decisions, and a plan
file is an executor handoff that needs the decision made first. **Plans 030–038
were then written at the maintainer's explicit request**, with the missing
decisions filled in as stated assumptions.

**Six of the nine are assumption-bearing** — 030 (step 3), 035, 036, 037, 038,
and 031 (its premise that the counts *should* add up). Each header carries an
"Assumptions this plan encodes" box naming the ticket that can overturn it. The
two worked examples:

- **030** assumes v3 *rejects* unknown config keys. Adding `.strict()` is one
  line and a **breaking change** for every config carrying a stray key, against
  a schema [#114](https://github.com/Gallevy/hermex/issues/114) is redesigning
  anyway. Steps 1–2 of that plan (a config with no default export silently
  becoming all-defaults) encode no assumption and stand alone.
- **037** assumes the matching semantics for Node builtins, `node:` specifiers,
  type-only imports, subpath imports and workspace protocol — all of which are
  the substance of [#108](https://github.com/Gallevy/hermex/issues/108). It
  deliberately builds the *axis* and stops short of the rule.

The three findings with no decision left were **already planned**: 013 (line
numbers are byte offsets), 016 (`parseFile` null contract), 022 (enricher
`findIndex`). The audit re-confirmed all three still reproduce on `688c481`.

**Retraction.** Finding 9 originally claimed file rules seeing a different file
set than the scan was a bug. It is not — file rules glob the whole repo by
design, to reach `.nvmrc`, `.babelrc`, `jest.config.*` and other files the scan
never parses; `fixtures/repos/all-rule-types/hermex.config.ts:11-12` says so
outright. Restricting them to `includes` would be a capability regression. No
plan was written for it; only the per-pattern glob cost stands, and it is
[#112](https://github.com/Gallevy/hermex/issues/112)'s to measure.

**Plan status changes from this audit:**

- **022 is partially stale.** Its step 3 deletes `config-v2/`, which
  [#125](https://github.com/Gallevy/hermex/pull/125) already removed (`fb3d171`).
  Steps 1 (dead `reports` field), 2 (enricher `findIndex`) and 4 (docs sync) still
  apply. Its drift check will trip on `config-v2/` — that is expected, not a STOP.
- **022's step 1 gained a caveat.** Deleting `AggregatedReport.reports` makes props
  detection *provably* unreachable rather than merely unused — `report.patterns.props`
  is built on every file and read by nothing else. Still correct to delete; see
  [#103](https://github.com/Gallevy/hermex/issues/103).

**Superseded by the map — do not re-plan from `plans/`:** every "Direction options"
entry below is now a map ticket (yarn berry → #121, SARIF/Action → #106, baseline
diff → #113), and "enable TypeScript strict mode" is **done** — `tsconfig.json` now
has `strict: true`. The one live item that section still holds is `.npmrc`
auto-discovery, which sits in the map's Not-yet-specified.

## Direction options (maintainer decisions, not plans)

Grounded suggestions from the 2026-07-04 audit. The maintainer's own
`docs/TODO.md` is explicitly marked "do not think about at the moment", so
none of these were planned; they are recorded so the evidence isn't lost.

- **Yarn berry (v2+) lockfile support** — the adapter currently returns an
  empty version map for berry lockfiles (Plan 022 fixes the misleading label).
  Berry lockfiles are YAML and `js-yaml` is already a dependency, so support
  is one adapter method away. Effort ~M.
- **Baseline/diff mode for `comply`** — teams migrating incrementally can't
  gate on "no *new* violations"; the `versus` feature shows the project
  already cares about migration tracking. Effort ~M.
- **SARIF output format** — `comply` in CI + a `sarif` value for
  `output.format` would give GitHub annotations without glue scripts. Additive,
  effort ~L.
- **GitHub Action / programmatic integrations** — the new library entry point
  (`src/index.ts`) and typed JSON result exist but nothing consumes them yet.
  A published Action would be the cheapest proof of the API. Effort ~L.
- **Enable TypeScript strict mode** — `tsconfig.json` has `strict: false` and
  `noImplicitAny: false` while `CONTRIBUTING.md:8` claims "strict type
  checking enabled". Real value, but a multi-file fix effort (L) with the TS
  7 RC pin in play — needs a maintainer go-ahead.

## Unplanned findings (real, but below the leverage bar)

- **SWC argument/element wrapper bug (fixed, Plan 025)**: discovered
  2026-07-10 during Plan 015's execution. `@swc/core`'s `CallExpression.arguments[i]`
  and `ArrayExpression.elements[i]` are `{ spread, expression }` wrapper
  objects; five pattern analyzers read `.type`/`.value` directly off the
  wrapper instead of `.expression`, so `advanced.lazy`, `advanced.dynamic`,
  `advanced.hoc`, `advanced.memo`, and `usage.arrays` detection was dead code
  on any input. Fixed in commit `d3e2656` (merged 2026-07-10) — kept here as
  the historical record since the plan file was deleted after landing.
- **Conditional pattern ignores JSX-branch ternaries** (found 2026-07-10
  during Plan 015): `analyzeConditionalExpression`
  (`src/swc-parser/patterns/conditionals.ts`) only matches `Identifier`
  branches, so `cond ? <Button /> : null` never populates
  `usage.conditional` (the component still appears in `usage.jsx`). Distinct
  from the Plan 025 wrapper bug — ternary branches are not wrapped. Extending
  it to JSX branches is a design decision (overlap with jsx usage tracking),
  not a bug fix; characterized by a test in
  `tests/swc-parser/patterns/conditionals.test.ts`.
- **Pipeline/command orchestration unit tests** — `runPipeline`,
  `executeScan`, `executeComply` have e2e coverage only. Mock-heavy unit
  tests are M-effort with moderate value while e2e pins exit codes and JSON
  output; revisit after Plans 019/020 settle the code.
- **Docs generation flow unclear** — `docs-templates/` + `scripts/update-docs.js`
  exist but no npm script or CI step runs them; generated outputs are also
  committed. Needs a maintainer decision on the intended flow before a plan
  is worth writing (Plan 022 Step 5 works around it defensively).
- **`.npmrc` / registry auto-discovery for releaseAge** — private registries
  ARE supported today via `releaseAge.registry` + auth token config; what's
  missing is auto-discovery from `.npmrc`. Nice-to-have, M effort.

## Findings considered and rejected

Rejected in the 2026-07-04 audit pass:

- **"Parallelize with Promise.all around parseSync"** (perf subagent's fix
  sketch): wrong — parseSync is synchronous; Promise.all changes nothing. The
  correct fix (async `parse()`) is Plan 019.
- **`console.error(error)` as a security finding**: overstated — a local CLI
  printing its own stack to its own user is not an exposure. Kept as a UX/
  consistency cleanup in Plan 020.
- **Configurable enricher concurrency (`CONCURRENCY = 8`)**: YAGNI until a
  user asks; revisit if registry throttling reports appear.
- **Env-var parsing style in enricher (TTL ternary)**: code is correct;
  pure style preference. Not worth a plan.
- **Type-only tests for `src/index.ts` exports**: `tsc --noEmit` (CI-gated by
  Plan 018) already fails on broken type exports; a tsd-style suite adds
  little.
- **"releaseAge unusable for private registries"**: partially false —
  `releaseAge.registry` and `authToken`/`HERMEX_REGISTRY_AUTH_TOKEN` cover
  it; only `.npmrc` auto-discovery is missing (see unplanned findings).
- **enforceOnBump graduated severities**: thresholds are already per-bump
  (patch/minor/major each have one); a second per-bump severity axis is
  speculative until requested.
