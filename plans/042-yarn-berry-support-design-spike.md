## Why this matters (product framing, not a bug)

`src/lock-parser/patterns/yarn.ts` currently claims
`supportedVersions = ['v1', 'v2+']` but only implements v1 parsing (via
`@yarnpkg/lockfile`, a v1-format-only library) — Berry (v2+) lockfiles
either fail to parse or silently return an empty version map. Plan 022
fixes the dishonest label (`['v1']`); this plan is the follow-up: build
actual Berry support. Berry lockfiles are YAML (unlike v1's custom format),
and `js-yaml` is already a project dependency (used by the pnpm adapter,
`src/lock-parser/patterns/pnpm.ts:3`), so the parsing primitive is already
in the dependency tree — this is squarely "the adjacent possible," not a
new integration.

## Current state

**`src/lock-parser/patterns/yarn.ts`** (full file, 79 lines) — the adapter
being extended. Key facts:
- `detect()` only checks for `yarn.lock`'s existence, not its format
  version — a Berry lockfile also matches this check today, meaning it's
  routed to the v1-only parser and silently degrades.
- `lockfile.parse(content)` (from `@yarnpkg/lockfile`) is the v1 parser;
  its `parsed.type !== 'success'` check is how v1-format failures are
  currently detected — but a Berry lockfile isn't necessarily a v1 "parse
  failure" in this library's eyes, it may parse as some degenerate/partial
  structure rather than erroring outright. **This needs to be verified
  empirically in Step 1**, not assumed.
- `parseMultiVersion()` mirrors `parse()`'s structure.

**`src/lock-parser/lock-file-adapter.ts`** — the interface:
```ts
export interface LockfileAdapter {
  name: string;
  supportedVersions: string[];
  detect(projectPath: string): string | null;
  parse(lockfilePath: string): Record<string, string>;
  parseMultiVersion?(lockfilePath: string): MultiVersionMap;
}
```
`detect()` returns a path or null — no format-version signal is threaded
through to `parse()`. Berry lockfiles have a distinctive header comment
(`# This file is generated by running "yarn install" with Berry` or a
`__metadata:` top-level YAML key, depending on version) that can
distinguish them from v1 at `detect()` time or at the start of `parse()`.

**`src/lock-parser/patterns/pnpm.ts:1-3`** — confirms `js-yaml` is already
imported and used for YAML lockfile parsing elsewhere in this codebase:
```ts
import { load } from 'js-yaml';
```

**`tests/lock-parser/lock-parser.test.ts`** and
`tests/lock-parser/fixtures/` — the existing test structure to extend; no
Berry fixture exists today (only `pnpm-lock.yaml`, `package-lock.json`,
`yarn.lock` — the last one presumably v1 format, confirm in Step 1).

## Steps

### Step 1: Obtain and examine a real Berry lockfile sample

Generate one (`yarn set version berry && yarn install` in a disposable
scratch directory with a couple of real dependencies — do this in your
scratch space, not the hermex repo) or use a well-known open-source
project's checked-in Berry `yarn.lock` as a reference (read-only reference,
do not commit a full copy of someone else's lockfile — extract just the
structural pattern needed for a fixture). Confirm:
1. The YAML top-level shape — is there a `__metadata:` key with a
   `version:` field indicating the lockfile format version?
2. How package entries are keyed (Berry uses a different key format than
   v1's `name@range` — typically `name@npm:range, name@npm:range2:` style
   with resolution info under each entry).
3. What `lockfile.parse()` (the existing `@yarnpkg/lockfile` v1 parser)
   actually does when given this content — does it throw, return
   `type: 'error'`/`'merge'`/`'success'` with garbage data, or something
   else? This determines whether Berry detection can happen via a failed
   v1 parse attempt or needs to happen before attempting v1 parsing at all.

Record findings in a short section at the top of the new fixture file's
adjacent test file (as a comment) or in the plan's own follow-up notes —
whichever is more natural, your call.

### Step 2: Decide the adapter structure

Based on Step 1's findings, decide (and justify in a code comment at the
top of the change): does Berry support belong in `YarnLockfileAdapter`
(one adapter, `parse()` branches on detected format) or as a separate
adapter class registered alongside it in whatever assembles the adapter
list (check `src/lock-parser/index.ts` for how adapters are registered and
selected)? Recommend keeping it inside `YarnLockfileAdapter` — both formats
share the `yarn.lock` filename and the `name`/`detect()` contract, and
`supportedVersions` already exists specifically to describe multi-version
support within one adapter — but verify `src/lock-parser/index.ts` doesn't
assume one lockfile-name-to-one-adapter-instance in a way that would make a
single branching adapter awkward.

### Step 3: Implement Berry parsing

Add a `parseBerryFormat(content: string): Record<string, string>` (and
`parseMultiVersion` equivalent) using `js-yaml`'s `load`, following
`pnpm.ts`'s existing pattern for YAML lockfile parsing as the style
reference. Branch `parse()`/`parseMultiVersion()` on the format signal
identified in Step 1 (e.g. presence of `__metadata:`), falling back to the
existing v1 path when that signal is absent.

**Verify**: `pnpm run typecheck` → exit 0.

### Step 4: Add a Berry fixture and tests

Create `tests/lock-parser/fixtures/yarn-berry.lock` (a minimal, hand-
trimmed real-structure sample — a handful of packages, not a full
real-world lockfile) and add a new `describe` block (or extend the existing
`YarnLockfileAdapter` block) in `tests/lock-parser/lock-parser.test.ts`
covering: `detect()` still finds it (same filename), `parse()` returns
correct versions, `parseMultiVersion()` collects multi-version conflicts if
the fixture has any, and — critically — the existing v1 fixture
(`tests/lock-parser/fixtures/yarn.lock`) still parses exactly as before
(no regression to the v1 path).

**Verify**: `pnpm run test:ci -- lock-parser` → all pass, including new
Berry tests and unchanged v1 tests.

### Step 5: Correct supportedVersions

Set `YarnLockfileAdapter.supportedVersions = ['v1', 'v2+']` — check
whether plan 022 already ran and changed this line to `['v1']`; if so,
change it back to `['v1', 'v2+']` now that it's genuinely true, and note in
your commit message that this supersedes plan 022's yarn label fix for this
one line.

**Verify**: `grep -n "supportedVersions" src/lock-parser/patterns/yarn.ts`
→ shows `['v1', 'v2+']`.

### Step 6: Full suite

```
pnpm run build && pnpm run test:ci && pnpm run typecheck && pnpm run lint
```

All exit 0.

## STOP conditions

- Step 1's investigation finds that `lockfile.parse()` (the v1 parser)
  throws an uncatchable/unexpected error type on Berry input rather than
  the `type !== 'success'` pattern the current code handles — STOP and
  report the actual failure mode; the detection strategy in Step 3 may need
  to happen *before* ever calling the v1 parser, not as a fallback from it.
- The Berry lockfile structure turns out to require resolving a dependency
  graph (not just a flat key→version list) to get correct per-package
  versions — STOP and report; that would be a materially bigger scope than
  this spike is sized for, and the maintainer should decide whether it's
  worth pursuing at that cost.
